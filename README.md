# Greengage-6-Reznik-Interconnect-Test

Локальный лабораторный кластер Greengage 6 и небольшой тест широких строк
Interconnect по предоставленным сценариям Резника. Четыре контейнера,
никаких отдельных mirror-хостов.

## Важные границы результата

- Базовая версия закреплена: **Greengage 6.30.1**, официальный release tag.
  Это воспроизводимая основа семейства GP6, а НЕ доказанный бинарный или
  функциональный эквивалент Arenadata DB 6.31. Сравнение с ADB требует отдельного
  прогона на реальном ADB 6.31. Номер ADB нельзя переносить на Greengage автоматически.
  При несовместимости параметра SQL тест прекращается: параметры не игнорируются.
- Репозиторий подготовлен без доступа к Docker daemon. Docker build, gpinitsystem,
  SQL, измерение сети и аварийное переключение здесь НЕ выполнялись.
  Успех реального запуска определяется логами на вашей машине, не этим README.
- 100 Gbit/s — настроенный верхний предел egress tc, не скорость физического
  устройства и не обещание фактической пропускной способности.
- Один компьютер/одна Docker VM остаются единой точкой отказа. Перекрёстные
  mirrors защищают от отказа контейнера сегмент-хоста, не от отказа компьютера.
- Здесь воспроизведён предоставленный сценарий; соответствие отдельной официальной
  методике с названием «тест Резника» не заявляется.

## Топология

| Контейнер | Назначение | Данные |
|---|---|---|
| master | coordinator/master | /data/master/gg-1 |
| standby | standby coordinator | /data/master/gg-1 |
| sdw1 | 4 primary + 4 mirror | /data/primary и /data/mirror |
| sdw2 | 4 primary + 4 mirror | /data/primary и /data/mirror |

Всего 8 primary + 8 mirror + master + standby = 18 процессов-инстансов БД.
Сегменты нумеруются content 0..7. Инициализация использует два hostfile-хоста,
по четыре DATA_DIRECTORY и MIRROR_DATA_DIRECTORY на каждом; gpinitsystem
располагает зеркала на другом хосте. Фактическое размещение и синхронность
жёстко проверяются SQL; не полагайтесь только на предположение о нумерации.
На штатной топологии каждый хост имеет 4 primary, 4 mirror; при отказе
одного сегмент-хоста на оставшемся может оказаться 8 активных primary.

## Минимальные ресурсы и требования

Профиль ограничивает master до 1 GiB, standby до 768 MiB, каждый sdw до 2 GiB;
итого 5.75 GiB лимитов контейнеров, по 1 CPU на контейнер. Это стартовые
лабораторные ограничения, не гарантированный минимальный объём памяти.
Для Docker VM разумно выделить от 8 GiB с запасом на ОС; сборка исходников
может потребовать существенно больше памяти и диска, чем запуск стенда.
При OOM сначала увеличьте SEGMENT_MEMORY до 3g или 4g; не отключайте mirrors.
Во время отказа одного sdw запас памяти особенно важен.

Нужны Docker Engine с Compose v2 (`up --wait`), git, make, Python 3 и bash.
Ориентир — Linux x86_64; установлен platform linux/amd64. На ARM требуется
эмуляция; скорость и поддержка сборки не гарантируются. Docker Desktop
использует Linux VM: tc действует внутри неё. Ядро должно поддерживать TBF.
Внешние порты БД не публикуются, SSH-ключи генерируются локально, пароль не нужен.
SSH host key checking отключён только для этого изолированного disposable lab.
Не подключайте сеть стенда к недоверенным клиентам.

## Быстрый запуск

```bash
cp .env.example .env
make verify
make build
make up
make init
make check
make network
make test
```

`make build` клонирует официальный tag с submodules, сохраняет commit в results,
собирает официальный ci/Dockerfile.ubuntu и затем runtime-образ. Первичная
сборка длительная; короткими сделаны тесты, не компиляция СУБД.
Версия / commit исходников фиксируются, но базовые Ubuntu-пакеты не snapshot-pinned:
это не обещание bit-for-bit воспроизводимости всего образа.
`install_and_configure_gpdb` из официального common.bash распаковывает бинарники;
путь /usr/local/greengage-db-devel проверяется при сборке.

`make init` запускается один раз на новых volumes. Повторная инициализация
поверх PG_VERSION запрещена. При ошибке init смотрите results/init.log и
`docker compose logs`; не считайте частично созданный кластер готовым.

После остановки/повторного создания контейнеров с сохранёнными volumes:

```bash
make up
make start
make check
```

Открыть shell gpadmin с окружением:

```bash
make shell
source /opt/lab/scripts/env.sh
psql -X -d adb
```

Если shell не загрузил greengage_path.sh автоматически, env.sh загружает его явно.
Все SQL и административные команды в автоматизации запускаются от gpadmin.

## Предоставленные файлы не исправляются на месте

`original/` содержит четыре предоставленных текстовых файла, включая README.
Тексты перенесены в UTF-8 с завершающим LF; исходных файлов-вложений для
побайтового сравнения не было. Неразрывные пробелы из сообщения сохранены.
SHA256.json фиксирует именно эти сохранённые тексты. Каталог монтируется read-only.

В исходном shell есть незакомментированные русские пояснения и команда psql,
разбитая на строки без backslash. В SQL присутствует count() без аргумента.
Запуск оригиналов как есть не используется и не объявляется успешным.

`scripts/prepare.py` создаёт отдельные рабочие копии в `work/`:

1. Нормализует NBSP в обычный пробел.
2. Комментирует пояснения в shell и восстанавливает продолжения команды psql.
3. Заменяет count() на count(*) в SQL.
4. Уменьшает row_count/candidate_count до 4096 и expected_hosts задаёт 2.
5. Уточняет комментарий о размере данных в рабочей копии.

SQL нагрузки и маршрутизации, session GUC и timeout 60s сохранены.
Все изменения видны в results/working-copies.patch. Оригиналы не переписываются.
Генерация повторяется перед тестом; редактировать work вручную бессмысленно.

## Небольшой прогон

Подготовка: 4096 строк по 1024 байта, около 4 MiB исходного payload на кластер
без учёта служебных данных и mirrors. Route candidates: 4096 чисел.
Контрольный запрос подготовки сохраняет множитель 32 из оригинала.
После подготовки выполняются:

- topology.sql: 8 primary, 8 remote synchronized mirrors, master и standby;
- route-host-check.sql и assert-routes.sql: ровно 8 уникальных межхостовых
  маршрутов, 0 внутрихостовых; нарушения останавливают тест;
- EXPLAIN VERBOSE для анализа Motion в фактическом плане;
- tcp 1 1 8 32 — первоначальный контроль: 1 сессия, 1 запрос;
- tcp 2 2 16 32 — небольшой параллельный прогон: 2 сессии по 2 запроса.

Используется IC_PACKET=65507 для TCP. Это параметр Interconnect, не MTU Ethernet.
MTU сети 1500. UDPIFC jumbo-профиль автоматически НЕ запускается:
8192 нельзя объявлять безопасным без сквозной проверки соответствующего MTU.

Положительное processed_bytes подтверждает SQL-обработку, но НЕ равно количеству
байт на сетевом интерфейсе. Время SQL включает CPU, построение широких строк,
план, сериализацию, память и сеть; по нему нельзя честно вычислить чистую
скорость Interconnect в Gbit/s. SQL-карта описывает предполагаемые направления;
Motion и реальные пересылки следует сверять с планом и при необходимости
счётчиками/захватом трафика. Короткий функциональный тест не доказывает насыщение 100G.
`REZNIK_FUNCTIONAL_TEST_OK` появляется только при нулевых exit codes всех шагов.

## Interconnect: настройка 100 Gbit/s и измерение

У Docker Compose нет штатного параметра `speed: 100Gbit`. Контейнер получает
NET_ADMIN; entrypoint применяет к eth0 `tc tbf rate 100gbit burst 16mb latency 50ms`.
Неподдерживаемое tc вызывает ошибку запуска, а не тихое продолжение без shaping.
Весь трафик контейнера идёт через одну bridge-сеть: cap общий для Interconnect,
репликации, SSH и прочих передач, НЕ отдельные 100G каждому сегменту.
Ограничение действует на egress каждого хоста, в обоих направлениях пары за счёт
настройки на обоих концах. Burst допускает кратковременные выбросы.

`make network` проверяет TBF в JSON на sdw1/sdw2 (100 Gbit/s = 12500000000 B/s),
проверяет ping с DF/1472 payload для MTU 1500 и запускает TCP iperf3
на 3 секунды в каждом направлении последовательно с одним потоком.
Результат — фактически измеренные Gbit/s, даже если это 2 или 10 Gbit/s, а не 100.
iperf проверяет TCP путь между контейнерами, а не производительность SQL Interconnect.
Тест network запускайте отдельно от нагрузки. MTU не меняется для имитации скорости.

Для настоящего подтверждения пропускной способности порядка 100G нужны достаточные
CPU/память, соответствующая сеть и отдельный измерительный эксперимент.
Локальные veth/bridge на одном компьютере физическую 100G-сеть не эмулируют.
Сеть фиксирована: 172.29.86.0/24. При конфликте меняйте subnet и все четыре адреса
в compose.yaml согласованно. IC_RATE меняется через .env, но network-проверка
намеренно требует именно 100 Gbit/s.

## Остановка и данные

```bash
make stop   # корректно остановить БД, контейнеры остаются
make down   # убрать контейнеры/сеть; named volumes сохраняются
```

Деструктивная очистка только вручную, когда данные больше не нужны:

```bash
docker compose down -v  # УДАЛЯЕТ ВСЕ ДАННЫЕ КЛАСТЕРА
```

## Проверка отказоустойчивости

Штатный make check проверяет размещение и синхронизацию, но не имитирует сбой.
Для отдельного ручного эксперимента после сохранения результатов можно остановить
sdw1 (`docker compose stop sdw1`), дождаться обнаружения отказа и проверить
SELECT count(*) FROM public.interconnect_universal_seed через master.
Факт переключения проверяйте в gp_segment_configuration, а не только по успешному SELECT.
После `docker compose start sdw1` требуется штатное восстановление mirrors
через gprecoverseg и проверка gpstate; возврат preferred roles при необходимости
выполняется gprecoverseg -r. Не запускайте make test до завершения восстановления:
проверка намеренно требует штатную сбалансированную топологию.
Standby coordinator сам по себе не обещает автоматическое переключение master:
активация standby через gpactivatestandby — отдельная административная процедура.
Восстановление после аварии и активация standby в данном архиве НЕ тестировались.

## Структура

```text
compose.yaml          четыре контейнера, лимиты, bridge MTU 1500, volumes
.env.example          версия, образ, CPU/RAM, tc rate
Makefile              команды стенда
README.md             эта инструкция
original/             предоставленные тексты и SHA256.json
work/                 генерируемые рабочие копии
scripts/              сборка, подготовка, init, проверки, сеть, SQL
  topology.sql        жёсткие проверки штатной топологии
  assert-routes.sql   жёсткие проверки маршрутов
  plan.sql            EXPLAIN VERBOSE тестового запроса
docker/               runtime Dockerfile и entrypoint
results/              логи, версии, patch, tc/iperf JSON
```

## Статус проверки архива

Запускайте `make verify` для локальных статических проверок. Они не требуют Docker.
Файл results/generation-validation.json описывает только проверки, выполненные
при генерации. Реальные результаты будут в init.log, check.log, reznik-test.log,
tc-*.json, iperf-*.json, network-summary.txt после запуска на вашей машине.
