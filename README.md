# Greengage-6-Reznik-Interconnect-Test

Локальный кластер Greengage 6 в Docker для небольшого TCP-теста широких строк Interconnect по сценариям Резника.

## Версия и топология

Базовая версия — Greengage 6.30.1. Полная эквивалентность Arenadata DB 6.31 не подтверждена.

| Контейнер | Назначение | Размещение |
|---|---|---|
| master | Координатор | `/data/master/gg-1` |
| standby | Резервный координатор | `/data/master/gg-1` |
| sdw1 | Сегмент-хост | 4 primary + 4 зеркала primary с sdw2 |
| sdw2 | Сегмент-хост | 4 primary + 4 зеркала primary с sdw1 |

Всего: 8 primary, 8 mirror, master и standby. Отдельных mirror-хостов нет. Размещение и синхронизация проверяются автоматически.

Все контейнеры работают на одном компьютере: зеркала не защищают от отказа самого компьютера или Docker VM.

## Требования и ресурсы

Нужны Docker с Linux-контейнерами и Compose v2 с поддержкой `up --wait`, Git, Bash и Python 3. Make необязателен: ниже приведены прямые команды.

Начальные лимиты:

| Контейнер | RAM | CPU |
|---|---:|---:|
| master | 1 GiB | 1 |
| standby | 768 MiB | 1 |
| sdw1 | 2 GiB | 1 |
| sdw2 | 2 GiB | 1 |

Суммарный лимит RAM — 5.75 GiB. Для Docker VM ориентир — от 8 GiB. Сборка может потребовать больше ресурсов, чем работа стенда. При OOM увеличьте `SEGMENT_MEMORY` в `.env`.

Образ настроен на `linux/amd64`. Сеть — `172.29.86.0/24`, MTU 1500. При конфликте адресов измените subnet и адреса контейнеров в `compose.yaml`.

## Быстрый запуск

Команды выполняются из корня проекта.

### Windows / Git Bash

Для исправленного `scripts/verify.py` перед проверками задайте:

```bash
export BASH_EXE="$(cygpath -m "$(command -v bash)")"
export PYTHONUTF8=1
```

Эти переменные нужно задавать в каждом новом окне Git Bash.

### Проверка, сборка и инициализация

Создайте `.env`, только если его ещё нет:

```bash
[ -f .env ] || cp .env.example .env

python scripts/verify.py
bash scripts/build.sh
bash scripts/lab.sh up
bash scripts/lab.sh init
bash scripts/lab.sh check
```

Первичная загрузка исходников и сборка могут быть длительными. Скрипт сохраняет commit Greengage в `results/greengage-commit.txt`.

`init` выполняется один раз на новых volumes. При ошибке смотрите `results/init.log` и `docker compose logs`. Частично созданный кластер не считается готовым.

## SQL-тест TCP

```bash
bash scripts/lab.sh test
```

Параметры Interconnect:

```text
gp_interconnect_type=tcp
gp_max_packet_size=65507
```

Рабочая подготовка создаёт 4096 строк по 1024 байта — около 4 MiB исходного payload без учёта зеркал и служебных данных.

Автоматически выполняются:

- проверка штатной топологии и синхронизации зеркал;
- проверка 8 межхостовых маршрутов и отсутствия внутрихостовых;
- сохранение плана через `EXPLAIN VERBOSE`;
- контрольный прогон: 1 сессия × 1 запрос, множитель payload 8;
- небольшой параллельный прогон: 2 сессии × 2 запроса, множитель 16.

Таймаут каждого нагрузочного запроса — 60 секунд. Лог: `results/reznik-test.log`.

Расчётный темп обработки payload описан в `metodics.md`. Это не прямое измерение сетевых байтов. Для расчёта по полному времени этапа необходимо отдельно зафиксировать интервал от запуска первого worker до завершения последнего: текущий нагрузочный скрипт выводит время отдельных запросов.

## Отдельный TCP-тест iperf3

Выполняйте без одновременной SQL-нагрузки:

```bash
bash scripts/iperf-tcp.sh
```

По умолчанию — по 3 секунды, один поток:

1. sdw1 → sdw2;
2. sdw2 → sdw1;
3. одновременно в обе стороны.

Вариант по 5 секунд с четырьмя потоками на направление:

```bash
bash scripts/iperf-tcp.sh 5 4
```

Результаты сохраняются в `results/iperf-tcp-<дата-время>-<pid>/`.

Используйте итоговые значения `receiver`. Для суммарной одновременной скорости складывайте только противоположные направления теста `bidirectional`. Не складывайте sender и receiver одной передачи или результаты последовательных тестов как одновременную скорость.

Скрипт требует установленного iperf3 с поддержкой `--bidir`.

## Сеть и предел 100 Gbit/s

При запуске контейнеров к `eth0` применяется:

```text
tc tbf rate 100gbit burst 16mb latency 50ms
```

Это верхний предел исходящего трафика контейнера, общий для Interconnect, репликации и остальных передач. Он не гарантирует достижение 100 Gbit/s и не имитирует физическую 100G-сеть.

Существующая команда:

```bash
bash scripts/network.sh
```

проверяет TBF, MTU 1500 и выполняет короткие последовательные TCP-тесты. Для отдельного измерения с одновременным обменом используйте `scripts/iperf-tcp.sh`.

## Исходные и рабочие файлы

- `original/` — принятые исходные версии тестов, README теста и `SHA256.json`.
- `work/` — автоматически создаваемые рабочие копии.
- `scripts/prepare.py` — нормализация пробелов, необходимые исправления и уменьшение объёма данных.
- `results/working-copies.patch` — различия между исходными и рабочими файлами.

Пояснения shell, продолжения команды `psql` и `count(*)` в актуальных исходниках уже исправлены. Подготовка сохраняет совместимость с предыдущими текстами.

Не редактируйте `work/`: он пересоздаётся перед тестом. После осознанного изменения `original/` пересчитайте `original/SHA256.json` и повторите проверку.

## Управление кластером

Открыть shell координатора:

```bash
bash scripts/lab.sh shell
source /opt/lab/scripts/env.sh
psql -X -d adb
```

Корректно остановить БД:

```bash
bash scripts/lab.sh stop
```

Убрать контейнеры, сохранив volumes:

```bash
bash scripts/lab.sh down
```

Повторный запуск с сохранёнными данными:

```bash
bash scripts/lab.sh up
bash scripts/lab.sh start
bash scripts/lab.sh check
```

Полное удаление данных — только вручную:

```bash
docker compose down -v
```

Последняя команда удаляет все данные кластера.

## Статус проверок

Статическая проверка на Windows / Git Bash пройдена: контрольные суммы, синтаксис Bash/Python и генерация рабочих копий.

Успешная сборка Docker-образа, инициализация БД, SQL-нагрузка, iperf3 и аварийное переключение пока не подтверждены результатами прогона.

`check` проверяет штатное размещение и состояние, но не имитирует отказ. Проверку аварийного переключения и восстановления выполняйте отдельным экспериментом.
