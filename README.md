# Greengage-6-Reznik-Interconnect-Test

Локальный кластер Greengage 6 в Docker для сравнения TCP и UDPIFC Interconnect на широких строках по сценариям Резника и проверки пропускной способности между сегмент-хостами через iperf3.

Архитектура, ресурсы стенда и результаты измерений приведены в [RESULTS.md](RESULTS.md).

## Версия и топология

Исходники собираются с `GG_REF=6.30.1`. Фактическая строка версии сервера: `PostgreSQL 9.4.26 (Greengage Database 6.0.0-beta.1 build dev)`. Полная эквивалентность Arenadata DB 6.31 не подтверждена.

| Контейнер | Назначение | Размещение |
|---|---|---|
| master | Координатор | `/data/master/gg-1` |
| standby | Резервный координатор | `/data/master/gg-1` |
| sdw1 | Сегмент-хост | 4 primary + 4 зеркала primary с sdw2 |
| sdw2 | Сегмент-хост | 4 primary + 4 зеркала primary с sdw1 |

Всего: 8 primary, 8 mirror, master и standby. Отдельных mirror-хостов нет.

Проверка штатной топологии требует размещения primary и его mirror на разных хостах, синхронизации зеркал и наличия standby.

Все контейнеры работают на одном компьютере: зеркала не защищают от отказа компьютера или Docker VM.

## Требования и ресурсы

Нужны Docker с Linux-контейнерами и Compose v2 с поддержкой `up --wait`, Git, Bash и Python 3. Make необязателен.

Пример профиля `.env` (фактические лимиты проверяйте через `docker compose config`):

```dotenv
COMPOSE_PROJECT_NAME=gg6-reznik
GG_REF=6.30.1
GG_IMAGE=gg6-reznik:6.30.1

MASTER_MEMORY=1g
STANDBY_MEMORY=1g
SEGMENT_MEMORY=4g

MASTER_CPUS=1
SEGMENT_CPUS=4

IC_RATE=200gbit
```

Ресурсы для приведённого примера:

| Контейнер | Лимит RAM | Квота CPU |
|---|---:|---:|
| master | 1 GiB | 1 |
| standby | 1 GiB | 1 |
| sdw1 | 4 GiB | 4 |
| sdw2 | 4 GiB | 4 |
| Всего | 10 GiB | 10 |

### Ресурсы компьютера и Docker

Тестирование выполнено на компьютере со следующими ресурсами:

| Параметр | Значение |
|---|---|
| Процессорные ресурсы | 16 ядер / 16 логических процессоров по данным ОС |
| Оперативная память | Около 32 GB |
| ОС | Windows 11 Pro |
| Среда выполнения | Docker с Linux-контейнерами под WSL 2 |
| CPU, доступные Docker | 16 логических процессоров |
| RAM, доступная Docker | Около 23,5 GiB |
| Настройка памяти WSL 2 | `memory=24GB` |

Лимиты работающих контейнеров подтверждены через `docker inspect`: по 1 CPU и 1 GiB RAM для master и standby, по 4 CPU и 4 GiB RAM для sdw1 и sdw2. Закрепление за конкретными ядрами не задано.

В `scripts/init.sh` установлено:

```bash
gpconfig -c gp_vmem_protect_limit -v 384
```

В нагрузочном запросе сохранено `statement_mem='128MB'`. Базовый функциональный тест использует 1–2 сессии.

Финальный стресс-профиль использует четыре сессии и множитель payload до 32. Один полный раунд TCP/UDPIFC прошёл успешно. В предыдущих запусках наблюдались отмены по VMEM при восьми сессиях и множителе payload 64, а также TCP-таймауты в трёхраундовых сериях.

Образ настроен на `linux/amd64`. Сеть — `172.29.86.0/24`, MTU 9000. При конфликте адресов измените subnet и адреса контейнеров в `compose.yaml`.

## Подготовка Windows / Git Bash

Все команды выполняются из корня проекта.

В каждом новом окне Git Bash перед проверками задайте:

```bash
export BASH_EXE="$(cygpath -m "$(command -v bash)")"
export PYTHONUTF8=1
```

Исправленный `scripts/verify.py` использует `BASH_EXE`, чтобы запускать Git Bash вместо WSL. `PYTHONUTF8` устраняет зависимость чтения текстов от Windows-кодировки.

В проекте добавлены `.gitattributes` для LF и исключения резервных копий и `.vscode/`. Файлы `original/` хранятся без преобразования окончаний строк.

## Сборка и первый запуск

Создайте `.env`, только если его ещё нет:

```bash
[ -f .env ] || cp .env.example .env
```

Проверьте файлы и итоговую конфигурацию:

```bash
python scripts/verify.py
docker compose config
```

Соберите образ:

```bash
bash scripts/build.sh
```

Первичное клонирование выполняется с историей и submodules, поэтому загрузка может быть длительной. Скрипт сохраняет commit Greengage в `results/greengage-commit.txt`. Контекст сборки исходников передаётся Docker как tar без распаковки на Windows.

Если сборка уже выполняется, не запускайте вторую параллельно.

Изменения скриптов, выполняемых внутри контейнера, не обновляют автоматически их копии в существующем контейнере. При необходимости обновите образ либо скопируйте изменённые файлы.

`reznik-series.py` и `reznik-stress.py` запускаются на хосте; копировать их в контейнер не требуется. Перед нагрузкой они вызывают `prepare.py` и читают нагрузочный shell-скрипт из `work/`. В логах сверяйте фактические параметры нагрузки.

После успешного завершения сборки выполняйте по одной команде:

```bash
bash scripts/lab.sh up
bash scripts/lab.sh init
bash scripts/lab.sh check
```

При ошибке не переходите к следующему шагу.

`init` запускается один раз на новых volumes. При ошибке смотрите `results/init.log` и `docker compose logs`. Частично созданный кластер не считается готовым.

Текущую загрузку контейнеров можно посмотреть командой:

```bash
docker stats
```

## SQL-тест UDPIFC

Запуск:

```bash
bash scripts/lab.sh test
```

Параметры Interconnect:

```text
gp_interconnect_type=udpifc
gp_max_packet_size=8192
```

Рабочая подготовка создаёт 4096 строк по 1024 байта — около 4 MiB исходного payload без учёта зеркал и служебных данных. Число кандидатов маршрутов — 4096.

Автоматически выполняются:

- проверка штатной топологии и синхронизации зеркал;
- проверка 8 межхостовых маршрутов и отсутствия внутрихостовых;
- вывод плана через `EXPLAIN VERBOSE`;
- контрольный прогон: 1 сессия × 1 запрос, множитель payload 8;
- параллельный прогон: 2 сессии × 2 запроса, множитель payload 16.

Подготовка также выполняет свой контрольный запрос с множителем 32.

Таймаут каждого нагрузочного запроса — 60 секунд. Лог: `results/reznik-test.log`. План запроса выводится в этот же лог.

Расчётный темп обработки payload не является прямым измерением сетевого трафика.

Одиночный тест выводит время отдельных запросов. Для измерения общего времени этапа workers и сравнения TCP с UDPIFC используйте серию:

```bash
python scripts/reznik-series.py 3
```

Скрипт выполняет подготовку и проверки один раз, затем запускает три раунда контрольного и параллельного этапов для каждого транспорта, чередуя порядок TCP и UDPIFC. Параметры пакетов: TCP — 65507, UDPIFC — 8192.

Результаты сохраняются в отдельном каталоге `results/reznik-series-<дата-время>/`. Файл `summary.csv` содержит параметры этапов, общее время `T_run`, основной показатель `B_run_Gbit_s` и дополнительный `B_avg_Gbit_s`. Для сравнения используйте медиану `B_run_Gbit_s` по раундам отдельно для каждого этапа.

## Стресс-тест TCP и UDPIFC

Сначала выполните один раунд:

```bash
python scripts/reznik-stress.py 1
```

После успешного прохождения можно запустить три раунда:

```bash
python scripts/reznik-stress.py 3
```

Подготовка данных и проверки выполняются один раз перед серией. В каждом раунде запускаются все этапы для обоих транспортов. Порядок TCP и UDPIFC чередуется.

Размеры пакетов: TCP — 65507, UDPIFC — 8192.

| Этап | Сессии | Повторов на сессию | Всего запросов | `payload_repeat` | `queue_depth` |
|---|---:|---:|---:|---:|---:|
| `control` | 1 | 100 | 100 | 8 | 32 |
| `sustained` | 4 | 100 | 400 | 16 | 32 |
| `heavy` | 4 | 100 | 400 | 32 | 32 |
| `endurance` | 4 | 100 | 400 | 32 | 32 |

`heavy` и `endurance` — два последовательных прогона одинакового тяжёлого профиля.

Результаты сохраняются в `results/reznik-stress-<дата-время>/`: `summary.csv`, логи этапов и `measured-load.sh`.

Показатели:

- `T_run_s` — полное время этапа в секундах.
- `B_run_Gbit_s` — суммарный логический payload, делённый на время этапа.
- `B_avg_Gbit_s` — расчётный показатель по среднему времени запросов.

`B_run` характеризует выполнение всей SQL-нагрузки, а не напрямую измеренный сетевой трафик.

В финальном успешном раунде средний `B_run` двух тяжёлых этапов составил 10,37 Гбит/с для UDPIFC и 39,93 Гбит/с для TCP. Результаты приведены в [RESULTS.md](RESULTS.md).

При ошибке работника серия останавливается. Неуспешные этапы исключаются из сравнения производительности. Не запускайте одновременно несколько нагрузочных тестов или iperf3.


## TCP-тест iperf3

Запускайте только после поднятия контейнеров и отдельно от SQL-нагрузки:

```bash
bash scripts/network.sh
```

Скрипт проверяет TBF и прохождение пакетов размером 9000 байт между сегмент-хостами в обе стороны, затем выполняет TCP-тесты по 3 секунды с одним потоком на направление:

1. sdw1 → sdw2;
2. sdw2 → sdw1;
3. одновременный двунаправленный тест.

Для одновременного теста скорость фиксируется отдельно для каждого направления.

Результаты:

```text
results/iperf-forward.json
results/iperf-reverse.json
results/network-summary.txt
```

Скорость определяется по итоговому значению `receiver`. Результаты последовательных направлений не складываются как одновременная скорость. Этот тест не измеряет UDPIFC Interconnect.

Средние результаты пяти финальных прогонов:

| Режим | Скорость, Гбит/с |
|---|---:|
| Последовательно: sdw1 → sdw2 | 37,65 |
| Последовательно: sdw2 → sdw1 | 69,55 |
| Одновременно: sdw1 → sdw2 | 20,66 |
| Одновременно: sdw2 → sdw1 | 16,87 |
| Одновременно: сумма двух направлений | 37,53 |

Максимальная однонаправленная скорость — 71,20 Гбит/с. Между прогонами наблюдался значительный разброс. Подробные результаты приведены в [RESULTS.md](RESULTS.md).

## Сеть и предел 200 Gbit/s

При запуске контейнеров к `eth0` применяется:

```text
tc tbf rate 200gbit burst 16mb latency 50ms
```

Это верхний предел исходящего трафика контейнера, общий для Interconnect, репликации и остальных передач. Он не гарантирует достижение 200 Gbit/s и не воспроизводит физическую 100G-сеть.

Проверка TBF, MTU, последовательные и одновременные двунаправленные TCP-замеры выполняются командой `bash scripts/network.sh`, описанной выше. Сетевой тест выполняйте без одновременной SQL-нагрузки.

## Исходные и рабочие файлы

| Каталог / файл | Назначение |
|---|---|
| `original/` | Принятые исходные версии тестов и README теста |
| `original/SHA256.json` | Контрольные суммы исходных файлов |
| `work/` | Генерируемые рабочие копии |
| `scripts/prepare.py` | Подготовка рабочих копий и уменьшение объёма данных |
| `results/working-copies.patch` | Различия между исходными и рабочими файлами |

В актуальных исходниках уже исправлены комментарии shell, продолжения команды `psql` и `count(*)`.

Подготовка нормализует неразрывные пробелы, уменьшает `row_count` и `candidate_count` до 4096, задаёт `expected_hosts=2` и транспорт по умолчанию `udpifc` в рабочем нагрузочном скрипте.

Для UDPIFC в рабочем нагрузочном скрипте устанавливается размер пакета по умолчанию 8192 байта.

Не редактируйте `work/`: каталог пересоздаётся перед тестом. После осознанного изменения `original/` пересчитайте `original/SHA256.json` и повторите:

```bash
python scripts/verify.py
```

## Подключение DBeaver

Драйвер: PostgreSQL.

- Host: `127.0.0.1`
- Port: `15432`
- Database: `adb`
- Username: `gpadmin`
- Password: пустой

В `init.sh` настроен доступ `gpadmin` без пароля со всех адресов для master и standby. Это настройка только для локального стенда. Порт Docker опубликован только на `127.0.0.1`.

## Управление кластером

Открыть shell координатора:

```bash
bash scripts/lab.sh shell
```

Внутри контейнера:

```bash
source /opt/lab/scripts/env.sh
psql -X -d adb
```

Корректно остановить БД:

```bash
bash scripts/lab.sh stop
```

Убрать контейнеры, сохранив volumes:

```bash
bash scripts/lab.sh down
```

Повторный запуск с сохранёнными данными:

```bash
bash scripts/lab.sh up
bash scripts/lab.sh start
bash scripts/lab.sh check
```

Полное удаление данных — только вручную:

```bash
docker compose down -v
```

Последняя команда удаляет все данные кластера.
